# 记忆这件事：从用现成的轮子到自己造一个

> 这个 bot 是个陪伴型的 Telegram AI——你跟它聊天就像跟一个网友聊天。
> 这篇讲的是：**怎么让它"记得"你**。两个月里我们换了一次方案，下面是为什么。

---

## 一、起点：聊得越久，越冷场

最早的版本，bot 跟你聊天时能"看到"的东西很有限——就是当下这条消息和最近十几句对话。聊一会儿能接得上，但**关掉聊天框过两天再开**，它跟一张白纸差不多。

具体翻车场景大概长这样：

- 上周聊了一半的事，今天问起来 bot 一脸茫然
- 你随口说过一句"别叫我宝宝"，过几天它又叫你宝宝
- 同一个梗你讲了三次，每次它都觉得新鲜——因为它不记得前两次

这是**陪伴型产品最尴尬的体验差距**。它不是"AI 不够聪明"，是 AI **没有关于你的过去**。一个人之所以能成为朋友，前提是 ta 记得你——记得你说过什么、喜欢什么、什么事让你不舒服。如果每次见面都要重新自我介绍，那不叫朋友，那叫客服。

所以**一定要有一层"长期记忆"**：能从对话里挑出值得记住的事、存下来、下次相关的时候捞出来用。这件事 LLM 自己不会做——它只会处理你当下塞给它的对话。**记忆得我们自己造**。

---

## 二、第一选择：找了个现成的轮子叫 memU

我们不是第一批做这件事的人。开源社区里已经有几个项目专门做"给 AI 加长期记忆"——`mem0`、`memU`、`Letta`（前身叫 MemGPT）。我们看了一圈，选了 memU。

理由很朴素：

**它的"记忆"形态跟我们的直觉差不多**。memU 把记忆切成"分类 + 条目"两层——比如分类叫"用户偏好"，下面的条目就是一句句具体的事实（"用户喜欢吃辣""用户在北京"）。这跟我们想要的差不多——把对话里值得记住的事提炼成一条条人话存起来。

**可以放在自己服务器上跑**。陪伴产品的对话不能上传到第三方公司，必须本地跑。memU 是开源的 Python 包，自己起服务就能用。

**省事**。它把"从对话里抽事实、存数据库、需要的时候搜出来"这一整套都打包好了。我们当时估算：自己写大概要两周，用现成的一周内能跑通最小可用版本。

接进去花了大概 4 天就跑通了。**对话体验立刻有了变化**——bot 真的能跨天回忆起几天前说的事，你提到一个名字它能补充背景。我们看到这个变化时还挺振奋——证明"长期记忆"这件事是值得做的，方向没错。

---

## 三、用着用着，发现哪里不对

接下来的 6 周，几乎每周都会撞到一两个 memU **跟陪伴 bot 实际需要不太一致**的地方。每次的处理方式都是"在它外面再包一层兜底"。包到第 4 层的时候，开始怀疑：是不是这条路走不下去？

下面是几个具体故事。

### 1. memU 假设记忆都是"客观事实"

memU 抽出的每条记忆都被当成"100% 准的客观事实"。但人和人之间的对话不是这样：

- 你说"她最近在追《三体》"——三个月以后还作数吗？也许她早就追完看别的了。
- 你某次心情不好时说"我不喜欢辣"——是真的不喜欢，还是当时胃疼？
- 两个月前你提过一次"想去日本"，之后再也没说过——这事还在心上吗？

人的话是**带不确定性的**。陪伴 bot 几乎每条事实都该带一点"我大概记得，但请你纠正我"的语气。**memU 的存储格式里没有给这种"不太确定"留位置**——它的字段就是"这是事实"，没有"这事我七分确定"。

直接的后果是：bot 会笃定地引用半年前你随口说的一句话，把你说得一脸懵。

### 2. 它怎么"抽"记忆是个黑盒

memU 决定"从对话里抽哪些东西、用什么格式存"的逻辑，是写死在代码里的。你想改这套逻辑，只能改它的源码。

我们是中文聊天场景，跟 memU 默认的英文对话场景不太一样——抽出来的"事实"经常是错的颗粒度（要么太细，要么把无关的话也抽进来）。每次想调整都要改它的内部代码，这种修补**积累得很快就是一笔技术债**。

5 月 6 号那次踩了一个最典型的坑：我们把抽取规则改成中文版，让它输出 JSON 格式；但 memU 内部解析的代码只认 XML 格式。结果是——**每次"抽取记忆"的接口都返回成功，但记忆表里 4 天没增加任何一行**。日志只是个 WARNING，调用方看不到任何错误。

我们以为一切正常，实际记忆完全没在工作。

直到查数据库的时候才发现这个事。这种**表面上没事、底下烂掉**的故障是最伤的——MVP 表面跑得好好的，用户体验告诉你"bot 好像记不住"，但代码层看不到错误。

### 3. 它"找记忆"的方式太单一

memU 找出"跟当前对话相关的记忆"用的是**一种方法**：把当前消息变成一串数字（行话叫"向量"），跟记忆库里每条记忆的数字算"距离"，挑最近的几条返回。

但**中文聊天里很多关键线索靠的是具体名词**：

- 你说"上次那个会议"——得按"会议"这个词去找，不是看整句话的语义。
- 你说"那个谁"指代之前提过的人——只靠"距离"算法根本搜不到，因为"那个谁"跟人名距离很远。

要解决这个，得**几种方法一起用、再合并排序**——按距离找一批、按关键词找一批、按具体名词找一批，然后综合排个名次。memU 不开放这一层，要扩展只能 fork（复制一份它的代码自己改）。

### 4. 它假设只有一个用户

memU 的接口里有"过滤这个用户"的字段，但**它内部的状态是按"全局只有一个用户"设计的**。我们 5 月 13 号上了多用户邀请制之后，立刻撞上：两个用户同时聊天时，memU 偶尔会把 A 的记忆错挂到 B 头上，触发数据库报错。

这是**设计层面的事**，单靠在外面加锁治不了根。

### 5. 总结一下

到 5 月中，回头看这 6 周的体验：**memU 解决了 80% 我不想自己写的事，但剩下 20% 全在它的设计假设之外**——

| 我们要的                | memU 给的                |
| ------------------- | ---------------------- |
| 带不确定性的记忆            | 100% 客观的事实             |
| 中文对话定制              | 写死的英文逻辑                |
| 多种方法一起找记忆           | 单一方法                   |
| 多用户隔离               | 假设单用户                  |
| 记忆有时效（"这条三个月后就别用了"） | 只有"什么时候被记下"，没有"什么时候过期" |

每加一条新需求，要么改它的源码，要么在外面再包一层。**包了一段时间发现：在外面包的代码量已经快赶上 memU 自己一半大了**——但还要顶着 memU 的格式跑，两边互相约束。这就有点尴尬了。

## 四、压垮骆驼的最后一根稻草

真正让我们决定换的，是想做一件**memU 怎么改都做不了**的事——给每条记忆加一个"我有多确定"的标签，并且让 bot **自动维护这个标签**。

具体来说：

- 一条新记忆刚存进去时，跟旧记忆比一下——如果跟"用户喜欢吃辣"打架（用户最近三次都说不能吃辣），就把旧那条标成"待确认"
- 下次 bot 想用"用户喜欢吃辣"这条时，先在心里问一遍："这事还作数吗？" 不确定就别用
- 凌晨 bot 闲下来时，把所有"待确认"的记忆过一遍——确认还作数的升回"确认"，确认作废的标成"过时"

这是个**让 bot 的记忆能自我反省**的机制。它需要：

- 数据库里加几个字段（这条状态、依赖哪些其他记忆、上次确认是什么时候）
- 写入新记忆时多跑一段冲突检测
- 取记忆时多跑一段反向验证
- 凌晨多一个定时任务批量整理

**每一条都跟 memU 的设计冲突**——它的格式没有这些字段，没有这种钩子，没有这种状态。

我们算了一下：fork memU 改 4 处，加起来的工作量，跟**自己从头写一张表 + 一组方法**差不多。后者甚至更轻——因为完全按自己的需求设计，没有兼容包袱。

更深一层的判断是：**memU 给的是"通用长期记忆"——它对所有需要长期记忆的 AI 都有点用。但它不是"陪伴 bot 的关系记忆"——多了不确定性、时效、情感这些维度**。继续在它上面打补丁，是用错位的工具解决正确的问题。

5 月 18 号，推倒重写。

## 五、自己写：到底搭了什么

新的版本就是一张表。这张表里每行存一条记忆，但比 memU 多了一些字段——这些字段就是上一节说的那些"memU 没法做的事"对应的位置：

- **这条还作不作数**——状态：确认 / 待确认 / 过时
- **我多确定**——0 到 1 的数
- **上次确认是什么时候**——避免反复确认
- **它依赖哪些其他记忆**——比如"用户在追新剧" 依赖"用户喜欢科幻"，前者过时不一定影响后者
- **关键名词**——LLM 抽完 LLM 自己列的名词，给"按名字找记忆"那条路用
- **什么时候开始有效 / 什么时候失效**——区分"被记下来的时间"和"在世界里有效的时间"
- **这是什么类型的记忆**——稳定特征 / 一时一地的事 / 跨多条事实总结出的观察

代码量：把"从对话抽记忆、存进表、需要时找出来、自动验证、夜里整理"都写完，加起来大概 1500 行。**比一开始想象的少**。

后面又加了几层，每一层都是因为**自己控制全部代码所以能加**：

- **三种方法一起找记忆 + 综合排名**——按"语义距离"找一批、按"关键词"找一批、按"名词"找一批，每条记忆得到一个综合分数
- **三因子打分**——找出来的记忆按"相关度 + 重要性 + 新鲜度"加权，避免老旧的记忆永远排前面
- **原始对话备份**——LLM 抽出来的"事实"是简化过的，但原始对话另存一份，必要时能查回去看 LLM 是从哪几句话提炼的
- **两个时间维度**——上面提的"这事什么时候开始有效"跟"什么时候被记下来"分开存
- **跨条总结**——凌晨让 LLM 看一周的事实，写出"她对工作有压力但不愿意主动说"这种**单条记忆里没有但是几条合起来能看出来的**观察

这几个想法都是从相关学术论文里学的（一篇叫 *Generative Agents* 的 Stanford 论文 / 一个叫 *Graphiti* 的开源项目），但**实现是自己写的**——因为每个具体的需求都跟 memU 的设计假设错位。

## 六、回头看这件事

**用过 memU 不算亏**。它让我们 4 天就跑通了"长期记忆"这件事的最小可用版本，看到接进去之后聊天体验的变化（明显比"只看最近对话"要好）。它让我们**看清楚方向**——确认了"长期记忆值得做"这件事。

**但它不是终态**。一旦想做更细的事——记忆带不确定性、多种方法一起找、有时效——自己写就是更短的路。

经验上，**判断一个开源轮子是不是该换掉**有几个信号：

1. **每次想加新功能都要改它的源码** —— 说明它没给你扩展的口子
2. **它的"基本单位"不是你想要的单位** —— memU 是"分类 + 条目"，我们要的是"事实 + 状态 + 依赖"。这是结构层面的错位，不是少一个 API 的事
3. **你已经在外面包了一层 wrapper 来弥补它没暴露的能力，wrapper 自己就快有它一半大** —— 这时候在维护两套代码
4. **撞上"它的设计假设跟你的产品定位错位"这种判断** —— 不是单点 bug，是体系性的不合适

**信号集齐三条以上，就该认真考虑换了**。等到累积一堆补丁才换会更痛——既要写新东西，还要从旧格式迁数据。我们 5 月中决定换的时候，已经有点晚了——那两周的"包 wrapper"工作量，相当于自己重写一次。

---

## 七、不是反开源轮子

这次最大的收获不是"自己写比用现成的好"——很多场景**现成的轮子就是首选**。

真正学到的是：**轮子的价值在于它的设计层度跟你的核心需求是否对齐**。

memU 的设计是"通用长期记忆"——对一个"做笔记 + 偶尔搜回去"的工具型 AI 是完美的。它对**陪伴关系记忆**就错位了——因为陪伴关系多了情感、时效、不确定性这些维度。错位不是 memU 不好，也不是 memU 设计有问题——是**两个产品的核心需求不在一个层面**。

下次再选第三方轮子时，会更早问自己：**它的"基本单位"是不是正好我要的单位？** 如果你已经在脑子里把它的输出再组合成你需要的形状，那它就不是合适的层。

> 轮子给你的是"它认为通用的形态"。你需要的是"你这个产品独有的形态"。两者对得上就用，对不上就别拖。

## 附录：memU 时代踩过的具体坑（归档）

> 以下是切自搭之前留下的具体技术笔记，给可能也在做类似集成的人看。
> 这些坑切完都不存在了，新人不需要读。

### A.1 strip-think 中间层

我们用的某个 LLM 输出会带一段 `<think>...</think>` 块（模型的"内心独白"）。memU 内部不知道剥这种格式，原始内容直接进数据库，导致记忆里全是"用户提供了一个分类的旧摘要..."这种乱码。

修法：本地起一个小 FastAPI 服务（`src/llm_proxy.py:18082`）作为 memU 跟真正 LLM 之间的中间层，永远剥 `<think>`。对没 think 块的模型是空操作。

### A.2 静默 XML / JSON 解析失败

中文版抽取规则让 LLM 输出 JSON，但 memU 内部 parser 期望 XML。返回的 JSON 找不到 XML 根标签 → 日志一条 WARNING → 接口仍返回成功 → 记忆表 0 增长。

教训：**集成第三方时要先验证最里层的 contract**——这条事实有没有真的进库，不能只看上层接口的返回值。

### A.3 macOS 系统代理污染

memU 内嵌的 OpenAI SDK 会被 macOS 的系统代理（Clash）劫持返回 502。修法：环境变量加 `NO_PROXY=127.0.0.1,localhost,...` 防止本地服务调用走代理。

### A.4 多用户隔离失败

memU 内部的状态在并发场景下有 race，跨用户记忆请求偶尔触发数据库外键冲突。**设计层面的多租户支持缺失**——靠应用层加锁治标不治本。这条加速了切自搭的决心。

### A.5 迁移脚本

老库 → 自搭：`scripts/migrate_memu_to_native.py`（一次性，幂等）。把 memU 的两张表转成新格式的一张表，重新计算每条的"语义向量"入库。
