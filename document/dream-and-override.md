# bot 的"夜里整理"和"个性化调教"

> 这篇讲的是：**怎么让 bot 在每个用户身上长出独一无二的样子**，
> 而不是所有人面对的都是同一个 AI。两个机制——夜里整理思绪、给每个人单独调教——是这件事的核心。

---

## 一、起点：bot 每次只看到当下，不够

bot 跟你聊天时，它"看到"的东西是当下这条消息 + 最近十几句对话 + 一点关于你的背景信息（兴趣、记忆、当下情绪判断）。这些**够它就这一句话给个体面的回应**。

但有些事，**单看这一轮是处理不了的**：

- 你上周说过"别叫我宝宝"——bot 这次该把这事记进自己的"行为说明书"，让以后所有对话都带上。这事不是一次对话能解决的。
- 你跟一般人不一样，**特别惜字如金**——平时回复就一个字。这种长期画像应该影响 bot 跟你聊天的整体姿态，但 bot 自己在每个 turn 是看不出"她整体特别惜字如金"的——它只看得到当下这句"嗯"。
- bot 最近一周在某种场景下**频繁翻车**——用户发"嗨"它就追问"昨晚睡得好吗"，老妈子模式。bot 怎么知道自己翻车了？它在每个翻车的当下都觉得自己说得很对。
- bot 突然想到一件事，第二天可能想跟你聊——这"想到"的过程发生在哪？bot 当下回完一句话就关机了，不会"独自待着想事情"。

这些都需要**跨多轮、跨多天的整理**——一个**人不在用户面前的时候 bot 还在做事**的过程。

我们叫这个过程 **Dream**——bot 的夜里复盘。

---

## 二、Dream：每天凌晨 03:13 让 bot 整理一遍思绪

每天凌晨 3 点 13 分，后台跑一个定时任务：对每个最近活跃的用户，跑一遍**整理流程**。

为什么放凌晨？两个原因：

- 白天 bot 忙着接话，没时间停下来想"我跟这个人最近聊得怎样"
- 凌晨 LLM 调用便宜（很多模型有低峰时段优惠），而且不影响白天对话延迟

为什么叫 Dream？因为**这就像睡觉时大脑整理白天信息**——把零散的事实合成画像、把白天没想清楚的东西凌晨想一遍、把过期的旧记忆扔掉。

实际跑下来，这个"整理"过程有 6 个不同的小段，每段处理一类事——

### 1. 给每条记忆做个体检

白天写新记忆进数据库时，如果它跟旧记忆**有冲突**——比如旧记忆说"用户喜欢吃辣"，但新对话里用户连续三次说"我不能吃辣"——bot 会把旧那条标成"待确认"。

凌晨这一段做的事：**把所有积攒的"待确认"记忆过一遍**。LLM 看一下相关上下文，判断它现在还作不作数。还作数的升回"确认"，不作数的标成"过时"。这是一次**记忆的盘点**，避免"待确认"无限累积。

### 2. 把零散事实合成画像

白天 bot 记下来的事实是单条的：「用户上周加班到 12 点」「用户今天又说很累」「用户提到老板在催进度」。

每条单看没什么。但**夜里 LLM 看一周的事实**，能写出"她最近工作压力很大但不愿意主动说"这种**跨多条事实才能看出来的画像**。这种"高阶观察"会被存成一种特殊的记忆，下次召回时一起用——bot 看到的就不只是"她加班了""她累了"这些零散事实，还有"她在压力下不爱主动说"这种**整体倾向**。

这个想法是从 Stanford 一篇叫 *Generative Agents* 的论文里学的——论文里 25 个 AI 角色在小镇里互动，每个角色每天夜里都跑一遍这种"反思"，让 ta 形成对周围人和事的高阶理解。

### 3. 整理用户偏好

白天用户陆续告诉 bot 一些偏好——"少反问"、"别叫我宝宝"、"用上海话聊"。这些偏好会被一条条加进 bot 的"行为说明书"，但**积累多了会冲突或重复**——"少反问"和"别问那么多"其实是同一回事，"用上海话"和某个之前说的"别说方言"打架。

这一段就是让 LLM 看一遍所有积累的偏好，**合并冗余、删掉过期、保留有效的**。

### 4. 让 bot 自己想"明天想跟她聊什么"

bot 看一周的对话，自己脑子里冒出 0 到 5 条**第二天可能想跟用户提的事**。**不是 reactively 抽热门话题，是它自己"想到了"什么**。比如：

- 「她在做 AI 陪伴产品时刻意避开恋爱感——想问问她是怎么实现这个的」
- 「她上次提到对洛克王国的舆论好奇——想跟她聊聊这事的最新进展」

这些想法第二天会被存着，等 bot 主动开口时拿出来用——让 bot 开口的内容**有"想了一晚"的痕迹**，而不是当下随机抓一个最近聊过的话题。

这部分参考了一个叫 [airi](https://github.com/moeru-ai/airi) 的开源项目（模仿 Neuro-sama 的 vtuber AI），它有一个机制让 AI 每隔一段时间被"触发"一次问自己"我现在想做什么"。

### 5. **bot 自己看自己最近聊得怎样，自己改自己的人格**

这是最大的一段，也是最近才加的（5 月 28 号）。

bot 看自己**最近一周**跟某个用户的所有对话，识别有没有翻车。如果有，**自己动手改**这个用户专属的"行为说明书"。如果改不了（涉及全局问题、需要人介入），就**写一条 issue 给开发者**。

举一个真实的例子：5 月 28 号第一晚跑出来后，bot 自己识别出某个用户**特别惜字如金**——平时回复就一两个字。它给这个用户专属的"开口规则"加了一段：

> 这位用户惜字如金。看到 ta 短回时，**不要再追问续旧话题**——之前翻过一次车："嗨" → "那个 AI 项目你做到哪步了" → 用户回 "hello?" 明显懵了。
> 优先发一句**自己的状态**（"困了" / "饿了"），或者**就发一个表情**，不强求 ta 回。

这是 bot **自己看 7 天对话看出来的趋势**——开发者可能注意不到（看不过来 N 个用户的所有对话），但 bot 看自己每个用户的历史看得到。

具体怎么实现的，详见 [`agent-self-iterate.md`](agent-self-iterate.md)。

### 6. 整理跨用户共享的"技能库"

这一段不是"针对某个用户"——是**全局的**。我们有一个跨用户共享的"技能库"——比如某个用户提的"周一早上提醒我吃药"如果泛化得好，会被存成一个"提醒类技能"，下次别的用户提相似需求时可以复用。

这一段就是凌晨让 LLM 看一遍这个技能库，去重、淘汰、合并。

---

**为什么所有反思都塞进同一个凌晨班车？**

最初只有第 1 段——给"待确认"记忆做体检。每加一段都来自一个具体痛点：

- bot 召回出零散事实拼不出"这人是谁" → 加了第 2 段
- 偏好越积越多互相冲突 → 加了第 3 段
- 看到 airi 的"自己想做什么"机制 → 加了第 4 段
- 我们改 prompt 改不过来 → 加了第 5 段
- 跨用户技能库需要整理 → 加了第 6 段

它们都是"**反思类操作**"——读一周积累的事实，输出对未来的调整。共享一个时间窗（凌晨）+ 一个更聪明的模型（这种判断质量比速度重要）+ 一套上下文是合理的。

> Dream 的底色：bot 白天忙着接话，夜里整理思绪。第二天醒来，人格更新一点点。

## 三、Override：调教这件事，三种粒度

"Override" 是我们对 **per-user 调教 bot 行为** 的统称——你跟 A 用户聊的 bot 跟 B 用户聊的 bot **不应该一样**，每个用户身上的 bot 都该长出一些独特的样子。

实际上"调教"这件事在不同时间尺度上发生，需要**三种不同粒度的方式**——

### 粒度 1：单句指令的追加

最早的方式。每条调教就是一句话——"对方不喜欢被反复追问细节，含糊回答就接受"。

这种**追加片段**怎么写进 bot 的"行为说明书"？答案是：装配 system prompt 的时候，**追加到末尾**。不动主体，只是末尾加一段约束。

**触发**：每次 flush（每聊几轮存档一次）后，一个子 agent 会自动跑一遍——它读这一批对话，听到"少反问"这种诉求就写一条偏好。开发者可以在网页后台审核。**颗粒度最小，自动化程度最高，频率最高**。

**适合的事**：用户当下表达的局部偏好——"以后别叫我宝宝"、"周一早上提醒我吃药"、"别说方言"。这些都不需要重写整个"行为说明书"，**附加一句话比改一段更精准**。

详见 [`feedback-agent.md`](feedback-agent.md)。

### 粒度 2：整段重写

后来加的。如果开发者发现"某个用户整体跑偏了"——比如 bot 跟这个用户聊得太热情过头，或者某种话题方式不合适——单条偏好补不了，得**重写整段**。

我们让"行为说明书"由 26 个 prompt 文件组成（人格基线、当下情绪指引、开场白指引、礼貌规则等等）。在网页后台，开发者可以**给某个特定用户重写这 26 个文件中的任何一份**——左边是默认版本（只读），右边是这个用户专属的版本。改完立刻生效，不重启。

**触发**：开发者手动改。**颗粒度最大，频率最低**。

**适合的事**：开发者想给某个用户调一个**整体语气**——比如"对小张更冷一点"——通过改"礼貌规则"那段来实现。这种系统级的调整，单条片段做不到，必须整段重写。

### 粒度 3：bot 自己改

最新的（5 月 28 号上）。bot 在凌晨整理时，**自己动用**前面"粒度 2"那个机制——**给某个用户重写某个 prompt 文件**。

具体来说，bot 有一个工具叫 `apply_prompt_edit`，它能直接写入"粒度 2"的那个数据库表。bot 自己看 7 天对话识别问题，自己动手改。改完开发者**一键回滚**，原话立刻回来。

**触发**：每晚一次，bot 自己。**颗粒度大，频率低，没有人工审批**。

**适合的事**：bot 自己看出来"这个用户特别惜字如金，我应该改'开场白指引'里的'低能量识别'那段"——这种**针对个人的细颗粒度优化**，开发者来不及看（用户多了一个个改不过来），但 bot 看自己每个用户的 7 天历史看得到。

---

**三种粒度的对比**：

| | 颗粒度 | 频率 | 谁写的 | 怎么写的 | 用在哪 |
|---|---|---|---|---|---|
| 1 追加片段 | 一句话 | 每次存档一次 | 子 agent | 自动 + 高风险的开发者审核 | system prompt 末尾 |
| 2 整段重写 | 一整个 prompt 文件 | 开发者偶尔调 | 开发者 | 网页后台编辑 | 替换整份 prompt |
| 3 bot 自己改 | 同 2 | 每晚一次 | bot 自己 | dream 时自己调用工具 | 同 2 |

**为什么需要三种而不是一种？** 因为"调教"在不同时间尺度上发生：

- **用户当下表达的偏好**——要立刻沉淀（不能等开发者上线）→ 粒度 1
- **某个用户整体跑偏**——要能整段重写（追加片段不够精准）→ 粒度 2
- **bot 看 7 天宏观行为看到的趋势**——要给它接管的能力（开发者来不及看）→ 粒度 3

**每种都解决前面解决不了的问题，但不能简单合并**：粒度 1 不能取代 2（颗粒度太小）；粒度 2 不能取代 3（开发者频率不够，且看不过来 N 个用户）；粒度 3 不能取代 1（dream 在凌晨跑，追不上当下用户表达）。

> 调教是 bot 跟每个用户之间长出的茧——刚开始薄薄一层（粒度 1），慢慢变厚（粒度 2），最后 bot 自己能编织（粒度 3）。

## 四、Dream 跟 Override 怎么连起来

Dream 段里第 5 段（bot 自己改自己人格）的工具，**写入的就是粒度 2 的那张表**。流程是：

```
凌晨 dream 时间
    │
    ▼
LLM 看一周对话反思
    │
    ▼
识别出问题（"这用户惜字如金，开场白不该续旧话题"）
    │
    ▼
调用 apply_prompt_edit 工具
    │
    ▼
写入"粒度 2"的数据库表（这个用户对"开场白指引"的专属版本）
    │
    ▼
明天 user 来聊，bot 装配 prompt 时拿到的是新版本
```

**这就是 dream 和 override 的连接点**——dream 是时间尺度（凌晨），override 是机制（粒度 2），bot 自己**用这个时间尺度去做这种粒度的调教**。

为什么不让 bot 自己改"粒度 1"（追加片段）？因为粒度 1 是子 agent 的领地——它在 hot path 听用户**当下说的话**沉淀。Dream 是看一周宏观行为反思，颗粒度天然在粒度 2。**两条路径不重叠**。

为什么不让开发者也走 bot 这套自动流程？因为开发者直接编辑更快——网页改完立刻生效。**自动化的角色是接管"开发者看不过来的部分"，不是替代开发者直接操作**。

## 五、回头看这套设计

回头看演进路径，每加一层都是承接前面做不到的事：

- **最初**：bot 只看当下 + 召回的记忆 → 它能聊但**不能"长出对每个用户独特的样子"**
- **加粒度 1**：能记住一些偏好，但开发者想做大改还是要改主体
- **加粒度 2**：开发者能 per-user 大改，但**只能开发者手动**
- **加粒度 3（L4 自治）**：bot 自己能在凌晨做这件事

**每加一层都是发现上一层不够才加的**。如果一开始就想做全部，会过度设计——因为不知道每层实际跑起来是什么样。**实际上是用了一段时间发现某层不够，再加下一层**。

---

## 六、保险丝在哪

bot 有自治权之后，问题就变成**怎么防止它把事情搞砸**。三道保险：

**1. 不能改的红线**——bot 自己改 prompt 时有几条字是不能删的（比如"不能说自己是 AI"）。改完后必须仍然包含这些字，否则系统拒绝写入。bot 改不掉这一层。

**2. 限速**——一晚最多改 5 处；每个 prompt 一周最多改 3 次。即使 LLM 抽风，也只能在窄窗口里抽。

**3. 一键回滚**——每条自改写入数据库时都带"改之前长什么样"的快照。开发者在网页后台一键 rollback，原话立刻回来。

第三条最重要——**所有自治都建立在"可逆"上**。一旦 bot 改坏了，开发者的反应路径必须是秒级的（点一下按钮）。如果回滚要 5 分钟手动操作，这种自治就该被关掉。

---

## 七、不是为了"AI 更智能"

这套机制听起来像"让 AI 自己迭代自己"，但它的真正动机更朴素：

**陪伴关系是不可复制的**——A 用户跟 bot 之间长出的样子，跟 B 用户跟 bot 长出的样子，**不应该一样**。如果用同一份"行为说明书"服务所有人，那 bot 跟你就只是"一个 AI 跟一个用户"——这就是通用 chatbot 的体验。

**Override 让每个用户身上长出独特的茧**——你跟 bot 聊得越多，它针对你的版本就越独特。**Dream 让这个长出过程自动化**——不依赖开发者全天候盯着每个用户的对话。

这两件事衔接起来，就是 bot 在每个用户身上**独立、持续、可逆地演化**。这是陪伴产品跟通用 chatbot **最本质的差别**——

> 关系不是凭空产生的，是被记住、被反思、被一点点刻进 prompt 里的。
