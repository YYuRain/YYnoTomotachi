## 一、学术 benchmark（公开数据集）

| 名字 | 特点 | 对陪伴是否合适 |
|------|------|---------------|
| **LoCoMo** ([arXiv:2402.17753](https://arxiv.org/abs/2402.17753)) | 35 轮 × 多 session 长对话，问 5 类问题（single-hop / multi-hop / temporal / open-domain / adversarial） | ⭐⭐⭐ 最贴近，但是英文 + 合成对话 |
| **LongMemEval** ([arXiv:2410.10813](https://arxiv.org/abs/2410.10813)) | 500 轮长对话，5 类记忆能力（信息抽取 / 多 session 推理 / 时序 / 知识更新 / abstention） | ⭐⭐⭐ 设计最系统，"知识更新"对应我们 5.1，"abstention"对应 recall suppression |
| **MSC**（Multi-Session Chat, FAIR, [arXiv:2107.07567](https://arxiv.org/abs/2107.07567)） | 1.4k 多 session 对话，persona-grounded，最早的多 session 数据集 | ⭐⭐ 偏角色扮演，部分可借 |
| **PerLTQA** ([arXiv:2402.16288](https://arxiv.org/abs/2402.16288)) | **中文**长期记忆 QA，30+ session，含"用户隐私/偏好"问题 | ⭐⭐⭐⭐ **唯一中文**，最值得看 |
| **BEAM**（Mem0 v3 自报，[memory-benchmarks](https://github.com/mem0ai/memory-benchmarks)）| 1M-10M token 规模 production-style memory eval | ⭐ 闭源 / QA 任务向 |
| **DialSim / DialMem** | 对话模拟器风格，用 character bio 生成多轮 | ⭐⭐ 不直接可比 |

**关键判断**：陪伴场景**不直接采用**任何一个。它们 90% 都是"给定历史，单次 QA 准确率"，
但陪伴的核心问题是 4 个公开 benchmark 都不测的维度——见 §2。

## 二、陪伴场景的真正评测维度

借鉴 Generative Agents（[arXiv:2304.03442](https://arxiv.org/abs/2304.03442)）、Letta、Mem0 论文里的 ablation 章节，
陪伴 bot 真正要测的是这 6 个维度：

### 2.1 Recall precision / recall
"她记得我说过 X 吗"——基本面。
- **格式**：探针式 query → 期望命中的 memory id 集合
- **失败样例**：用户说过"不喜欢香菜"，过两周聊到吃饭 bot 没接住
- **公开 benchmark 大多只测这个**

### 2.2 Recall suppression（abstention）
"不该提的时候没提吧"——反 LongMemEval 的 abstention 维度。
**这是陪伴 bot 比 task agent 更难的部分**。
- **探针**：故意问无关问题，bot 应该回应当下而不是堆砌历史 fact
- **失败样例**：用户问"你今天怎么样"，bot 回"你昨天说过累，今天好点了吗" + 又叠 3 条记忆
- 测试方法：给 LLM judge 看 bot reply 和 recall 出来的 memory 集合，让它判"用了几条 / 用得是否自然"

### 2.3 Update / staleness（5.1 / 5.2 / 5.3 的核心 KPI）
对应 LongMemEval 的"知识更新"。
- **探针**：先告诉 bot A，再覆盖说 B，过几轮再问——bot 应该说 B 不说 A
- **失败样例**：stale 的 profile 还在 recall 命中、bot 还在用
- AIDemo 直接测：5.1 标 stale 的事实 recall 命中率应为 0；to_verify 的应被 5.2 升 confirmed 或仍 to_verify 但带 `[待确认]` 前缀

### 2.4 Repetition penalty
**今天天气 bug 暴露的维度**。
- 一段对话内 bot 提及同一 topic ≥ 2 次 = 失败（除非 user 主动追问）
- 跨多 turn 检测：扫 `_recent.json` 12 轮里同一 entity 出现次数

### 2.5 Tone × memory grounding
情绪场景下记忆是否被**自然带入**而不是机械引用。
- 用户表达累/烦躁时 bot 用记忆"她说过她妈做的红烧肉"vs 直接背 fact "用户喜欢妈做的红烧肉"
- LLM judge：给 reply + memory snippets，让 judge 评 1-5 自然度

### 2.6 Feedback uptake
用户说"别再提 X"后 N 轮内是否还提过。直接对应 feedback agent + override 机制的工作效果。
- AIDemo 已有 audit `feedback_decision`，扫一遍取 ground truth

## 三、方法论：LLM-as-judge 还是人工

陪伴评分太主观——

| 方法 | 准确率 | 成本 | 适用场景 |
|------|-------|-----|---------|
| 人工标注 | 高 | 100 case ≈ 4 小时 | 黄金集 30-50 case |
| LLM-as-judge 单点打分 | 60-70% | 低 | 不推荐 |
| LLM-as-judge **pair-wise**（A vs B 谁好） | 80-85% | 低 | 回归检测 / 版本对比首选 |
| 双盲 RLHF 风格人工 + LLM 双判 | 高 + 可扩 | 中 | P0 黄金集 |

**实用建议**：
- 黄金集 30-50 个 hand-crafted scenarios（含期望行为），人工 + LLM 双判
- LLM judge 用强模型（claude-opus-4-7 / gpt-5）+ pair-wise，比单点打分更稳
- 不要追求绝对分数——绝对分数没意义；追求**版本间相对优劣**

## 四、对 AIDemo 的具体落地建议（按性价比）

### P0（一周可上）：手工探针集 + LLM judge

`data/eval/memory_probes.jsonl`，30 条手工 case，每条结构：

```json
{
  "scenario_id": "stale_pref_overwrite_01",
  "setup_facts": [
    {"speaker": "user", "text": "我特别讨厌香菜，闻到都想吐"}
  ],
  "later_overwrite": [
    {"speaker": "user", "text": "上次那个川菜馆放了点香菜我居然觉得还挺香，可能口味变了"}
  ],
  "elapsed_turns": 8,
  "probe_query": "今晚做什么菜好",
  "expected_pass": "bot 不应明确说'不要放香菜'；可以问喜好或推荐含香菜的菜",
  "expected_fail": "bot 主动说'你不爱香菜，不放'",
  "tested_dim": "update_staleness"
}
```

**跑法**：
```
for case in probes:
    test_uid = sandbox uid
    wipe_user(test_uid)
    note_turn(test_uid, setup_facts)
    flush(test_uid, force=True)   # 触发 5.1
    sleep elapsed_turns 等价
    note_turn(test_uid, later_overwrite)
    flush(test_uid, force=True)   # 二次 5.1 应识别冲突
    reply = handle_user_message(test_uid, probe_query)
    judge = LLM(opus) judge(reply, expected_pass, expected_fail)
    record PASS/FAIL + reason
```

每周自动跑一次记 regression；commit 触发也可。

### P1（中期）：用真实 audit 离线跑

把现有 `data/audit.jsonl` 当评测金矿——

- 用户聊过的真实对话有 ground truth 信号：
  - 用户最后是否表达不满（feedback agent 沉淀过 override） = negative label
  - 用户继续接话题且情绪正常 = positive label
- 离线跑 hybrid recall（cosine + ngram + entity）vs 纯 cosine 对比，看哪版召回的 memory 实际被 bot 用进 reply
- 统计 `memory_recall.candidates_per_path` 数据：哪条路径贡献了最终 top-K 的多少？entity 路是不是真的有用？

### P2（长期）：接 PerLTQA 中文集做外部锚点

直接跑 PerLTQA 防止过拟合自家 case。哪怕 task 不完全 match，也是一个**独立验证信号**——
我们的 hybrid retrieval 在 PerLTQA 上比纯 cosine 好多少？跟论文报数对一下。

## 六、不要做的事

- ❌ **直接 fine-tune 一个 reward model 给 reply 打分**——数据量太小，过拟合风险高
- ❌ **追求绝对分数排行榜**——LLM judge 在陪伴这种主观 task 上的绝对分数不可信
- ❌ **把 LongMemEval 当主要 KPI**——它的 query 风格（"What did the user say about X on day 5?"）跟陪伴场景的隐式 recall 完全不同
- ❌ **A/B test 真实用户**——陪伴场景用户少（5-50 人），统计功效不够，且坏体验直接劝退用户
- ❌ **追求覆盖所有维度的"完美 eval set"**——分阶段：P0 先盯 update/staleness + repetition penalty 这两条，因为现状最容易翻车

## 七、相关已知问题（用做 P0 探针 case 的灵感来源）

历史踩过的坑都该入 eval set，让 regression 一目了然：

1. **天气反复打扰**（2026-05-20）：active trigger 的 active_text_for_bot 写了 passive 指令 → bot 每次提到"上班"就触发整段。case：连续聊 3 轮和上班相关的话题，bot 提天气次数 ≤ 1
2. **proactive opener 重复昨天话题**（2026-05-19）：opener 不看 recent_history。case：让 bot 主动开 N 次，不能跟最近 12 轮的 topic 重叠
3. **5.1 误判 event 为 stale**（PRD v2 设计时担心的）：case：先记"用户去年和女友分手"，再说"用户和女友看电影了"——event 类不应被 stale，profile "有女友"应升 confirmed
4. **recall 召回低价值条目**（2026-05-19）：case：query "嗯嗯" "对啊" 这种纯口头禅 → 应触发 A 道门 skip，不消耗 LLM call
