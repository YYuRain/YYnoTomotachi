## 2. 主聊天模型 → claude-sonnet-4.6

5/8 评测后选的 kimi-k2.6 用了几天发现**容易混淆上下文**——用户说 A，下一轮回复指代 A 时常错位。换 sonnet-4.6 后这个问题消失。

### 一些观察

模型在评测里跑出的"风格分"（natural / persona）跟实际**长程对话表现**不严格相关。评测样本是 22 个独立场景，每个上下文短；真实对话是 12+ 轮 rolling window，模型能不能稳定 anchor 到角色 + 不混淆历史，是评测看不到的维度。

后来反思：评测**高分但实际不好用**的模型，往往是"短场景表演型"——单条回复抓得住人话气质，但跨多轮维持稳定性差。下次评测要补上 multi-turn 一致性这个维度。

memU 抽取/分类用的轻量模型也从 MiniMax 切到 `deepseek/deepseek-v4-flash`（单价 $0.14/$0.28 per 1M token，比 minimax 还便宜，质量足够）。

> **意味着**：评测榜单第一名不一定是日常陪你聊天的最佳人选。短场景能秀的模型在跨十几轮对话之后未必稳得住。后台跑后台抽记忆这种"判断对就行不要文采"的活，反而该用更便宜的小模型。**让贵的模型只做需要它的活，便宜的活别浪费**。

## 3. 记忆栈推倒重写

这是这两周最大头的工作。

### 为什么不用 memU SDK

之前用 [memU](https://github.com/NevaMind-AI/memU) Python SDK 跑长期记忆——它内部管 chunking / embedding / cosine recall。问题是：

- **SDK 内部决策是黑盒**：它怎么判 ADD / UPDATE / DELETE，外部看不到、改不动
- **多用户 FK bug**：memU 的 client 实例不分 uid，跨 uid 调用串数据
- **prompt 不可控**：抽取 prompt 烤在 SDK 里，想加"输出 entities"字段做不到
- **schema 不能扩展**：要加 `status` / `depends_on` / `valid_to` 等字段必须 fork SDK

5/18 决定撤掉 SDK，单表 `memories` 自己实现。**公共 API 不变**（`recall` / `note_turn` / `maybe_flush`），上层调用零改动。容器名 / env (`MEMU_DB_URL` / `MEMU_CHAT_MODEL`) 全部沿用旧名——避免下游 docker-compose / .env 改动。

> **意味着**：从"用别人的黑盒"换成"自己的小屋"。bot 的"长期记忆"现在每一条都看得见——它怎么写进去、什么时候被失效、有哪些条目互相依赖、为什么这次召回的是这条不是那条——全部可观测。坏处是要自己负责调优，但好处是出问题能查、想改能改。

### PRD v2 三层防线

参考 5/14 写的设计思考（`关于记忆-202605141721.md`）：

> RAG 结构扁平没有权重——近期的与久远的事同一层级、重要的与日常琐事是同一层级。
> 当前市面上的记忆框架存的是单个事实，而非事实之间的关系。其中一个事实变了，依赖它的记忆不会自动更新。这是记忆"可信赖"的关键瓶颈。

[MEME 论文](https://arxiv.org/abs/2510.10398)（2025/10）评测六个记忆系统在 Cascade（级联推理）和 Absence（消亡推理）上的表现——**全军覆没**：默认配置下 Cascade 平均 3%、Absence 平均 1% 准确率。换更强 prompt、加更深 retrieval、换更强 LLM 都关不掉这个 gap。**唯一能闭合的是文件 agent + Claude Opus + 全量上下文**，成本 70× baseline，不实用。

> 这表明，当前记忆能力的门槛不在于模型，而在于记忆架构没有提供充分的信息。

落地到代码就是三层防线：

| 层 | 触发时机 | 做的事 |
|---|---|---|
| **5.1 写入冲突检测** | 每条新事实 flush 后异步 fire | LLM 跑影响分析对最近 top-5 语义邻居判定 still_valid / to_verify / stale；老条目按结果 UPDATE status + depends_on 数组（去重 append 新事实 id） |
| **5.2 召回反验证** | recall 命中 to_verify 时同步阻塞 | LLM 反向验证（条目 + deps 上游 + 当前 query）；两态 still_valid / uncertain（不能直接判 stale 防错杀）；30min cooldown 用 last_verified_at 限速 |
| **5.3 Auto Dream** | 03:13 cron 批量 | 三态判定（与 5.1 同语义但允许激进判 stale，因为后台无打扰）；override 整理；P1-6 insight 生成；skill 库整理 |

`memories` 表加列：`status` (confirmed / to_verify / stale) / `confidence` / `last_verified_at` / `depends_on UUID[]`。recall 时 stale 完全过滤，to_verify 带 `[待确认]` 前缀让主 LLM 自己拿捏。

> **意味着**（用一个具体例子）：bot 之前记得你"住北京 / 通勤 15min / 办了理发店会员卡"。某天你说"我搬上海了"——
> - **5.1（异步）**：刚写入"住上海"这条新事实后，后台立刻去翻最近相关的旧记忆，发现"通勤 15min"和"理发店会员"都跟"住北京"有关——把它们标 `to_verify` 并记下"依赖于'住北京'这条"。
> - **5.2（同步）**：下次你跟 bot 聊到通勤，bot 召回"通勤 15min"——因为状态是 `to_verify`，召回时同步再让 LLM 想一遍："这条还成立吗？" 不确定的话给前缀 `[待确认]`，让 bot 在用这个事实时知道"我不一定准"。
> - **5.3（凌晨清理）**：03:13 跑批次，把所有 `to_verify` 条目重判一次——确认还成立的恢复，确认失效的标 `stale` 不再召回，但**不删**，留底以便事后复盘。
>
> 三层加起来想做的事：**让 bot 知道自己不确定**——不是装作什么都记得，而是该犹豫时会犹豫。

### 关于"模型不靠谱"的设计妥协

5.1 / 5.2 / 5.3 都依赖 LLM 判断"哪些条目相关 / 怎么影响"。**这本身就不可靠**。但"完全不做依赖维护"的代价更大——MEME 论文里 0% 准确率的级联推理，意味着 bot 永远不会主动注意到"用户搬家了 → 通勤时间该重新问"。

妥协是**把 LLM 判断的犯错代价降到最低**：
- 5.1 判 stale 直接写 `valid_to` 但同时保留 `status='stale'` 字段——双层语义，将来可恢复
- 5.2 不准直接判 stale（"反向验证"两态而不是三态）防错杀
- 5.3 后台跑无打扰，可以激进判但会留 audit 痕迹

### P0/P1 借鉴升级（5/20）

读完 `me/记忆框架横纵分析.md` ——把 Mem0 / Letta / Graphiti / Cognee / LangMem 的 README 实拉一遍 + 经典论文综述——把高 ROI 的借鉴点列出来分批做：

- **P0-1 hybrid retrieval**（Mem0 v3 借鉴）：cosine + ngram(ILIKE/pg_trgm) + entity 三路 RRF 融合（k=60）。Mem0 v3 [关键反转](https://arxiv.org/abs/2509.20021) 是放弃 ADD/UPDATE/DELETE 写入决策，回到 ADD-only + 强 hybrid retrieval（LoCoMo +20 / LongMemEval +27 准确率，写入路径还简化）。这跟前面"模型不靠谱所以少做写入决策"的方向一致
- **P0-2 三因子 ranker**（Generative Agents 借鉴）：在 RRF 上叠加 `final = α·rel + β·imp + γ·rec`，α=1.0 / β=0.3 / γ=0.3，τ_profile=180d / τ_event=14d。time-decay 让"上周聊过的事"自然比"两个月前提一句"更容易被召回
- **P0-3 命名一统**（LangMem 借鉴）：术语统一 hot path（同步阻塞 turn）/ background（异步 flush 后）/ procedural memory（prompt_overrides + skills）；admin UI 调教 tab 加 LangMem 命名 tooltip
- **P0-4 episodes provenance**（Graphiti 借鉴）：新 `episodes` 表存 raw turns；`memories.source_episode_id` 反查；admin UI 加"当时聊了啥"链接——一条事实从哪轮对话来的，可追溯
- **P1-5 bi-temporal**（Graphiti 借鉴）：`memories.valid_from / valid_to` 两列；判 stale 时 `valid_to=now()`（保留 status='stale' 双层语义）；recall 三路 SELECT 加 `(valid_to IS NULL OR valid_to > now())` 过滤
- **P1-6 insight 生成**（Generative Agents reflection 借鉴）：Auto Dream 03:13 第 3 段抽样最近 90 天 confirmed memory 让 sonnet 写 1-3 条**跨条目高阶观察** + supporting_ids → INSERT 为 `memory_type='insight' confidence=0.8 depends_on=supporting`。实测 admin 跑出的 insight：「工作上进取、睡眠困难模式、饮食随意将就」——supporting_ids 准确，是从 8 条 profile + 12 条 event 抽出来的

> **意味着**（P0/P1 这一组的整体效果）：bot 不再是"用关键词搜你说过的话"。它会综合三种方式找记忆——语义相近、文字相近、人物/物品同名——然后按"跟当前话题多相关 + 这条事实多重要 + 多久之前发生的"加权排序。同时它**会自己半夜睡一觉做整理**：白天写下的事实凌晨被回看一遍——失效的标失效，零碎事实被串成"这个人最近一阵子的状态"。再调起来时，bot 看到的不止是孤立事件，还有"你这两周睡眠不太好"这样的高阶观察。

```
hot path (同步阻塞 turn)                background (异步 / cron)
──────────────────────────              ───────────────────────
recall(uid, query)                       maybe_flush(uid)
  ├ ngram + entity + cosine 各 top-20      ├ 写 episode (raw turns)
  ├ RRF 融合 (k=60)                        ├ _extract_items (LLM 抽 profile/event/entities)
  ├ 三因子 ranker (α·rel + β·imp + γ·rec)  ├ _persist_items (embed + INSERT)
  ├ valid_to 过滤                          └ _fire_conflict_check (5.1 异步)
  └ 5.2 反验证 (命中 to_verify)
                                         auto_dream (03:13 cron)
                                          ├ 5.3 三态判定 (写 valid_to)
                                          ├ override_dream
                                          ├ P1-6 insight 生成
                                          └ skill_dream
```

### 一些反思

记忆这事做完最大的体会是**两类决策必须分开**：

- **检索决策**（hot path）必须快、必须准、必须确定性强——错召率高用户会觉得 bot 翻旧账或张冠李戴
- **写入决策**（background）允许慢、允许试错、允许保留多状态——后台慢慢演化比"实时强行判 stale"要稳

之前 memU SDK 把这两类混在一起做——recall 时它会顺手做一些写入决策（更新 last_recalled_at 之类），结果是 hot path 慢、写入路径不可观测。自搭栈把两条路分清楚后，每一步都能 audit、能补、能改。

## 4. 调教（feedback agent）+ skill 库

陪伴 bot 一个核心问题：**不同用户希望 bot 不同**。"别叫我宝宝"、"少反问"、"用上海话"、"以后下班前下雨提醒我带伞"。这些诉求让用户**不需要技术介入就能调** bot 的行为。

### 数据模型

新建两张表：

- `prompt_overrides(user_id, text, reason, source_skill_id, risk_level, status, trigger_kind, cron_schedule, condition_prompt, ...)` —— per-user 偏好沉淀
- `skills(name, summary, body, embedding, created_by, usage_count, ...)` —— 跨用户复用的 prompt 片段（仓库语义；只有跨用户实际复用过才 +1 usage_count）

### 流水线

flush 后异步 fire `_fire_feedback_check`：

1. **SCREEN**（aux LLM，deepseek-flash）粗筛——抓"用户表达偏好/不满/能力诉求信号"的那 batch turns
2. **候选 skills cosine top-3**——已有 skill 库里有相近的就考虑 reuse
3. **JUDGE**（main LLM，sonnet）精判——三态：忽略 / 沉淀为 override / 沉淀为 override + 添加 skill
4. **代码 regex 二次硬护栏**——7 条红线（关闭核心能力 / 改身份 / 泄漏内部 / 假冒 / jailbreak 措辞 / 一次性请求等）双层兜底
5. **risk_level 分流**：low 直接 active；high 走 pending 等 admin webUI 审核

### Active trigger 通道

"以后 X 时 / 如果 Y 就..."这种条件式诉求是 bot 的能力盲点——passive 通道（用户开口才回）做不到"用户没说但到点了我应该说"。

加了独立通道：`prompt_overrides` 加 `trigger_kind` (passive | active) / `cron_schedule` / `condition_prompt` / `last_fired_at`；新模块 `triggered_reach.py` 每分钟扫 active trigger，cron match 后 sonnet 判 condition + 生成消息：

- user 5min 内活跃 → 暂存 `pending_reach_messages`，下轮 user 回话时 `pop_pending_reach_for_merge` 拼进 user 消息当 `[系统暗示]` 段，bot 自然融入
- user 不在聊或暂存超 5min → 兜底直发

不走 proactive 冷却（独立 dedupe 走 `last_fired_at` 90s 防抖）。

> **意味着**：用户说一句"以后下班前下雨提醒我带伞"，bot 把这件事记下来，每天到下班前查一下天气，下雨就自然地说"今天下班前可能下雨记得带伞"——不下雨就不出现。如果你正好在跟它聊别的，它不会直接打断，而是把"该提醒"这件事融进当前对话里说出来——真朋友的处理方式。

### 一些反思

调教系统设计反复纠结的点是 **prompt baseline vs per-user override 的张力**：

- 把所有偏好都沉淀进 override → 老用户的 system prompt 变得臃肿，新用户冷启动很弱
- 把高频偏好提炼成 baseline → baseline 改一次影响所有用户，回滚困难

最后落到**两层结构**：baseline (`prompt/system_baseline.md`) 不动；用户自己的 override 段尾追加；跨用户复用的模式提炼成 skill 进 skill 库（cosine 召回时 `prompts.build_system_prompt` 自己挑相关的拼上）。

另一个反复打磨的点是**护栏**。LLM 判得很多时候判得过激（把用户随口一句"啊烦死了不想理你"判成"用户要求关闭主动通道"沉淀进 override）。最终方案是：
- prompt 层 7 条硬约束 + 8 个具体反例
- 代码层 `_HARD_FORBIDDEN_RE` regex 兜底
- LLM 判 high risk 的一律 pending（不管 LLM 觉得多想沉淀都先压住）

中间还出过事故：`active_text_for_bot` 字段被 sonnet 写成 passive 指令——"如果对方聊到出门/上班/下班...你顺手查天气"——这种 passive injection 让 user 说"上班"就触发。改 prompt 加"硬约束"段禁 passive 注入 + 把已沉淀的过期 override 标 disabled。

## 5. 工具栈整修（5/19 → 5/21）

之前 bot 调工具走 aux LLM detect 路径——turn 头跑 deepseek 判要不要搜 → 主 LLM 看着结果回。问题是：

- **决策不一致**：aux 判 needed=false，主 LLM 看不到结果但还是说"等我搜一搜"——空话
- **诊断难**：tool 调用全 0 chars，挖了半天才发现容器没装 mcporter / xhs（本地是 nvm/pipx 全局 binary，镜像里没这套）

### 5/19：工具栈整修

所有工具收敛到 `JINA_API_KEY` 一份依赖 + 容器零额外 binary。

- `read_url(url)` → Jina Reader (`r.jina.ai/<url>`)
- `search_web(query)` → Jina Search (`s.jina.ai/?q=...`) + `X-Respond-With: no-content`
- xhs / Exa / mcporter 都退役（账号风控 / 容器没装）
- URL 自动路由 `_fetch_one_url` 按域名分发（保留确定性逻辑，不走 LLM）

> **意味着**：bot 看链接、搜网页都靠一个 API key 走 Jina（一家做"AI-friendly 网页读取"的服务）；用户扔过来 URL 自动按域名分到对应读取器，不需要 LLM 判"这是什么域名"——这种确定性逻辑 LLM 反而不靠谱。

### 5/19：prompt 层修一组

- `_TOOL_DETECT_SYSTEM` 加运行时今天日期 + "今年是 2026 query 必须用 2026"——修 LLM 写 query 用旧年
- 加"试探口吻"识别：用户用"你能查 / 你试试 / 你帮我搜"等附带具体话题 → needed=true（之前会判 false 当作"问能力"）
- `_ROLE_DISCIPLINE` 新增"你有联网能力"段——明确告诉 bot 它有 read_url / search_web 工具；禁止主动声称"AI 不联网"（sonnet 默认人设错觉）
- `_maybe_fetch_context` 不管 needed 与否都 audit 一条 `tool_decision`，方便回查"为啥没触发搜"

### 5/21：native tool_use——主 LLM 自己直接调

aux detect 路径用了一段时间发现底层问题没解决——bot 还是会说"等我搜一搜"但实际没触发。原因是 aux 跑在 turn 开头一次性判，**主 LLM 之后说"我搜下"是它的语言生成，跟 aux 决策不同步**。两层 LLM 各做各的，体感就是"言行不一"。

5/21 改 [native tool_use](https://docs.anthropic.com/claude/docs/tool-use)——主 LLM（OpenRouter 或 Anthropic）通过原生 tool calling API 自己决定调不调、调什么；agent 收到 `tool_calls` 就执行工具、把结果喂回去让主 LLM 写最终回复。**每 turn 最多 1 次工具循环**避免成本失控（陪伴 bot 不需要 ReAct 多轮）。

`tools.TOOL_SCHEMAS` 注册 5 个工具：

| 工具 | 实现 |
|---|---|
| `search_web(query)` | Jina Search |
| `search_xhs(keyword)` | [`xiaohongshu-cli`](https://pypi.org/project/xiaohongshu-cli/)（jackwener，含签名）；cookie 持久化在 compose volume |
| `search_bilibili(keyword)` | [`bilibili-cli`](https://pypi.org/project/bilibili-cli/)（jackwener）；anon 搜不需 cookie |
| `read_url(url)` | Jina Reader |
| `read_github(query)` | curl + `api.github.com/repos/...`（gh CLI v2 强制 auth 不能 anon，已弃） |

借了 [Panniantong/Agent-Reach](https://github.com/Panniantong/Agent-Reach) 的工具选型把 xhs / bili 两个之前"退役"的搜索通过 jackwener 的 CLI 装进容器接回来。

> **意味着**：bot 现在能自己上小红书 / B 站 / 全网搜，行为前后一致——它说"我搜下" 就真的去搜，结果回来才开口。aux LLM detect 整条路径退役。

### 5/21：silent fail bug——`_TOOL_FUNCS` key mismatch

native tool_use 上线后实测 search_web 返空——audit 显示 `chars=0` 且**0 秒返回**。先怀疑 timeout race（curl `--max-time 15` vs subprocess `_TIMEOUT=8` 撞 race，外层提前 SIGKILL 让 stderr 被吞），加了 timeout buffer。还是空。

最后查到 dispatch table 的 key 写错了——`agent._TOOL_FUNCS = {"web_search": tools.search_web, ...}`（旧 aux detect 时代命名）但 `TOOL_SCHEMAS` 注册的 name 是 `search_web`。主 LLM 用 schema name 调 → `_TOOL_FUNCS.get("search_web") → None` → silent 返空字符串。**完全没 stderr 也没 timeout，就是 dict key 查不到**。

修：key 改名 + 未知工具 `log.warning` 兜底（之前 silent 没人发现）。同时 timeout buffer 那个修复也保留——subprocess 套 curl 的双层 timeout 必须外比内大 ≥3s，这是另一个真问题。

> **意味着**：一类工程坑——register 时叫 `search_web`、dispatch 时查 `web_search`，dict miss silent 返空，跟"工具坏了"看起来一模一样。日志层面要有"未知工具" warning 兜底，不然下一次同类问题还得挠头半天。这条进了我的 feedback memory 跨会话留底。

## 6. 主动触达调优（5/20 → 5/21）

主动通道改了几个小但要紧的点：

### 5/20 加新硬门：连续没回应 backoff

之前的 bug：admin 数据被错清后 `last_interaction` = inf，consecutive_asst 在 `_recent` 里能看到——但软门 LLM 看不到这个信号，反复发同一句 opener 没人回。加新硬门：连续 N 条 assistant 没等到 user 回应就 backoff，**直接看 `_recent` 实际状态**而不依赖 last_interaction 表。

> **意味着**：bot 能识别"我连发好几条没人理"这件事——会自动闭嘴一段时间，不会像跳针一样反复戳人。

### 5/20 decide LLM 喂 recent + active overrides

之前 decide 选 opener_angle 时只看话题热度——容易选个刚聊完的话题作为切入，让 user 觉得"这不是已经说过了"。改成把最近 12 条对话片段 + active overrides 喂进去，让 LLM 知道"已经聊覆盖过的话题别选"。

> **意味着**：bot 主动找话题时不会重复"刚才已经聊到的事"——选话题更接近朋友间的"想起来了"而不是"按列表点名"。

### 5/20 冷却参数调短

用户冷却 1h → 30min；自冷却 90min → 60min。原因是 admin 在测试时反复嫌"等太久"才能看到下一次主动——开发体验比保守好。

### 5/20 prompts 减"刻意"感

`_EMPATHY/INTEREST/DEPTH_DIRECTIVE` 之前有 positive examples（"可以说 嗯 / 那确实 / 我就是！"）。LLM 复读 example 让 bot 听起来在演网友——刻意。改成保留"不要 X" 黑名单 + 删 positive examples，让 LLM 自己想措辞。

> **意味着**：之前 prompt 里告诉 bot "可以这么说"——bot 会照搬例子里的话出现，听起来反而像在演。删掉之后只留"不要怎么说"的黑名单，让模型自己想——出来的话反而更松弛。给 LLM 列举正面例子是让它"模仿"，给反面例子是让它"避开"——后者更接近真人的语言生成方式。

### 关于"主动"的反思

主动这事调的越久越觉得**频率不是核心问题，时机才是**。

- 频率高用户烦不是因为"次数多"，是因为"在不该说的时候说"——周一上午 9 点收一条"在干嘛"会比凌晨 1 点收一条还烦
- 让 LLM 看 `user_active_score`（按用户历史活跃曲线学习）+ 当前时间，比"23-7 一刀切禁夜"准很多——半夜活跃用户夜里收消息正常
- 但**纯靠 LLM 判时机** LLM 又会给出过保守判断（"现在该睡了不打扰"）

5/20 这版的折中是：硬门拦掉肯定不该的（30min 内对方刚聊过、上次主动 1h 内），其他全交给 LLM 软门 + audit 出来事后看 LLM 判得准不准。

### 5/21 硬门软化为概率门

5/21 又往前走了一步：把所有原硬门统一软化为**概率跳过**。每个违规算一个 `skip_prob`，取最大那个掷骰子；封顶 0.97——保证最差也只是降频不会完全不主动。

| 违规类型 | skip_prob 曲线 |
|---|---|
| user_cooldown（对方刚聊过） | idle=0 时 0.95 → 30min 时 0.5 → 之后 0 |
| self_cooldown（自己刚发过） | 同形状，参考线 60min |
| daily_cap | 刚到 0.85，每多 1 条 +0.04 |
| unanswered_streak | 1 条 0.70 / 2 条 0.85 / 3+ 0.95 |

> **意味着**："硬门"原本是"任一违规直接拦死"——结果是某些边界 case（比如刚清空数据 + 系统冷启动）会让 bot **整段时间一句话都不说**。改成概率跳过之后，最严重组合（每日超额 + 连续 3 条没回）skip_prob 还是 0.97，但仍有 ~3% 概率突破——bot 永远不会变成"哑巴"。频率衰减很自然，audit 里能看到 `proactive_soft_gate_passed` 事件标"突破了"。

### 5/21 share_discovery：bot 主动逛网找有趣内容分享

之前主动通道只能"基于 user 历史话题写开场白"——bot 没有"我刚看到 X 想分享给你"的能力（prompt 也明确禁止编造"刚刷到"，因为以前会 hallucinate 假新闻）。

5/21 加新通道：每次 proactive tick，决策 LLM 可以输出 `share_intent={platform, query}`——指定要去哪个平台搜什么。如果 share_intent 不空，agent 就调对应工具搜，把原始结果给另一个 LLM 让它**挑一条最 fit user 画像的** + 写一段 ≤30 字的"为什么这条会戳到"理由（blurb），然后走新 prompt `chat_proactive_opener_share_ctx.md` 生成"朋友顺手转链接"风格的开场白。

约束：
- xhs / 小红书各每日 **1 条独立配额**（防同平台刷屏）；web 不限但仍计入总 DAILY_CAP
- 每个 platform 当日已用过就从 `share_quota_remaining` 列表里去掉，提前喂给决策 LLM 让它知道"今天 xhs 已经分享过了别再选"
- 选不出来（搜空 / LLM 觉得都不够戳）silent 降级到 topic_chat 老路径，不让 fire 空跑
- 老 prompt"不要假装刚刷到"的禁令在 share 模式被显式覆盖——**这次是真搜的**，可以说"刚搜到一条挺有意思的"

> **意味着**：bot 不再只在用户开口时才出现。它会自己刷小红书、刷 B 站、刷全网——遇到觉得你会喜欢的就转给你看，像群里朋友顺手发链接那样。每天每平台 1 条不会刷屏。配合记忆栈里"用户最近聊过什么"作为搜索 query，命中率会越来越准——这是"陪伴感"方向的第一步：让 bot **真的有自己的注意力**，而不是只反应用户的注意力。

## 7. 重大事故：误清 admin 数据

5/20 用户让"清空 admin 的数据"——我从对话上下文推断 admin = 8120470097（错的，这是普通用户；admin 真实 uid = 8058993786）。13 条 memory + 24 turns + 313 audit 行不可恢复。

事后写两条 feedback memory：
- `feedback_admin_uid_caution.md`：操作"admin 数据"前必查 `ADMIN_CHAT_ID` env 或 `users.note='admin'`，不要从对话推断
- `feedback_wipe_must_backup.md`：任何用户级 DELETE 之前先 dump 到 `data/wipe_backup_<uid>_<ts>/` 保 7 天

教训：**破坏性操作必须有 backup + uid 双重确认**。这一类操作不该走"我猜你说的是 X"的快路径。

> **意味着**：以后我（claude code agent）再被要求"清空 X 的数据"，会先查 env / 表确认 X 是哪个 uid，再先 dump 到 backup 目录留 7 天才执行 DELETE。这两条规则进了我的长期记忆系统，跨会话生效——下次新开窗口的 agent 也会读到。
